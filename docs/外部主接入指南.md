# 外部主智能体接入指南（bridge 协议）

> 适用对象：任何想把本项目当"手脚 + 工人"用的外部智能体（TRAE / Cursor / Claude Code / 自研脚本等）。
> 核心理念：**谁启动并驱动本项目，谁就是主智能体**；项目提供本地工具（shell/文件/MCP/Skill）、
> 池内模型工人（纯文本执行器）、完整多智能体任务编排。

---

## 1. 概念速览

| 角色 | 谁 | 干什么 |
|------|-----|--------|
| 主智能体（大脑） | **你（外部驱动者）** | 拆解任务、调用工具、调度工人、汇总把关 |
| 本地工具（手） | 本项目 | run_shell / 文件读写 / list_dir / MCP 工具 / Skill |
| 工人（苦力） | 智能体池里其它模型 | 纯文本执行器：单派、并行、投票、流水线 |

扫描二维码不用扫码，一句话：**你在外脑，项目当外包。**

## 2. 快速开始

### 2.1 配置 API（先用起来）

本项目按「中转站」组织模型：**一个 Endpoint + 一个 Key，可挂多个 Model**（一个站=一个免费 token 多模型）。

**第一步**：复制并填写密钥样例（`.env` 以点开头，AI 约定不读、git 不提交）：

```powershell
Copy-Item .env.example .env
```

`config.yaml` 的 `agents` 引用这些变量，示例（与 .env 配套）：

```yaml
agents:
  - name: node-a                      # 中转站 A：一个 token，多模型
    base_url: ${NODE_A_ENDPOINT}
    api_key: ${NODE_A_KEY}
    models: ${NODE_A_MODELS}          # 逗号分隔多个模型，模型可带 @上下文长度
  - name: node-b                      # 中转站 B
    base_url: ${NODE_B_ENDPOINT}
    api_key: ${NODE_B_KEY}
    models: ${NODE_B_MODELS}
```

`.env` 里填：

```ini
NODE_A_ENDPOINT=https://你的中转站a/v1
NODE_A_KEY=sk-你的token
NODE_A_MODELS=gpt-4o-mini@128k,claude-3-haiku@200k
NODE_B_ENDPOINT=https://你的中转站b/v1
NODE_B_KEY=sk-你的token
NODE_B_MODELS=kimi,glm-4-flash
```

**上下文长度参数**：每个模型可独立标注上下文窗口，格式 `模型名@长度`：
- `@128k` → 128×1024=131072 token；也可写纯数字如 `@200000`（200k）
- **不标 `@` 的模型按默认 128k 处理**
- 作用：历史对话按此窗口自动裁剪（上限=窗口×75%，给回复/工具调用留余量），
  小窗口模型自动少带历史防溢出，大窗口模型能带满上下文
- 以上 4 行配置实际展开为 4 个智能体：`node-a:gpt-4o-mini`（131072）、
  `node-a:claude-3-haiku`、`node-b:kimi`、`node-b:glm-4-flash`

**临时屏蔽某个模型**（中转站免费模型经常变，注释即下线，不改代码不重启）：

```ini
NODE_A_MODELS=gpt-4o-mini@128k,claude-3-haiku@200k,#mixtral@32k
```

规则：`models` 里 **`#` 前缀的模型直接跳过**（`#` 后不能有空格，否则会串进模型名）；加回模型删掉 `#` 即可。屏蔽语法可与 `@` 混用（`#mixtral@32k` = 下线一个标过窗口的模型）。

**自动展开**：上面会展开成 4 个智能体 `node-a:gpt-4o-mini`、`node-a:claude-3-haiku`、`node-b:kimi`、`node-b:glm-4-flash`。后续 `ask` 的 `agent`、`ask_many`/`ask_vote` 的 `workers` 直接按这些名字引用。旧写法（`model:` 单模型字段）仍然兼容。

改完 `.env` / `config.yaml` 后**重启 bridge 生效**。

### 2.2 启动 bridge

```powershell
# 在项目根目录（配置好 config.yaml 的 agents / API key 之后）
uv run python -m agent bridge
```

### 2.3 协议格式

- 传输：stdin / stdout，UTF-8
- 格式：**每行一个 JSON**（请求行 → 响应行，一一对应）
- 启动后第一件事：读一行 `ready` 事件确认握手成功
- **stderr 也保证 UTF-8**：配置警告等诊断走 stderr，bridge 启动即把 stdout/stdin/stderr 归一为 UTF-8（Windows 重定向流默认 GBK，不转码会让按 UTF-8 收 stderr 的驱动方解码报错）。stdout 永远是纯 JSON 行，诊断绝不混入。

**握手示例**（用任意方式读 stdout 首行）：

```
输入：   （无，启动即返回）
输出：   {"ok":true,"event":"ready","version":"0.1.0","agents":["glm-flash","kimi"],"mcp":[]}
```

### 2.4 最小调用

请求行：

```json
{"cmd":"ping"}
```

响应行：

```json
{"ok":true,"version":"0.1.0","agents":["glm-flash","kimi"]}
```

## 3. 指令全表

### 3.1 信息类

| 指令 | 说明 | 示例响应关键字段 |
|------|------|------------------|
| `ping` | 探活 | `ok, version, agents` |
| `list_agents` | 智能体池清单 | `ok, agents[{name,model,note}]` |
| `list_tools` | 可用本地工具 | `ok, tools[{name,description}]` |
| `list_sessions` | 存活会话列表 | `ok, sessions[]` |

### 3.2 工具与技能

| 指令 | 说明 |
|------|------|
| `{"cmd":"call_tool","name":"run_shell","args":{"command":"dir"}}` | 执行本地工具（工具名以 list_tools 为准） |
| `{"cmd":"load_skill","name":"技能名"}` | 读取技能全文（frontmatter + 正文） |
| `{"cmd":"run_skill_script","skill":"技能名","script":"脚本.py","args":{}}` | 执行技能内脚本 |

MCP 工具以 `mcp__<服务器>__<工具>` 命名，同样走 call_tool。

### 3.3 工人调度

| 指令 | 说明 |
|------|------|
| `{"cmd":"ask","agent":"glm-flash","prompt":"...","system":"可选角色"}` | 单派一个工人 |
| `{"cmd":"ask","prompt":"..."}` | 不指定 agent 时退回兜底单模型 |
| `{"cmd":"ask_many","workers":["w1","w2"],"prompt":"..."}` | 并行派多个工人，返回逐份结果（缺省 workers 用池内全部） |
| `{"cmd":"ask_vote","prompt":"...","threshold":0.5}` | 两步投票：先各出方案 → 再编号投票 → 超阈值宣布共识并附胜出方案全文 |

### 3.4 完整任务编排

| 指令 | 说明 |
|------|------|
| `{"cmd":"run_pipeline","task":"...","stream":true}` | 固定流水线：起草 → 评审 → 修订（不选主，池内全部当工人） |

### 3.5 持久会话

| 指令 | 说明 |
|------|------|
| `{"cmd":"new_session","session_id":"可选","orchestrator":"可选","tools":["白名单"]}` | 建会话；不传 session_id 自动生成； 传 `tools` 可做**会话级工具隔离**（只开放白名单内工具） |
| `{"cmd":"chat","message":"...","session_id":"...","stream":true}` | 用指定会话跑一轮，**历史自动接续**（JSONL 落盘） |
| `{"cmd":"list_sessions"}` | 列出存活会话 id |
| `{"cmd":"session_tools","session_id":"..."}` | 查某会话的工具白名单（allowed_tools）与被裁剪项（removed_tools） |
| `{"cmd":"close_session","session_id":"..."}` | 关闭会话并释放 Agent/MCP 连接 |

会话用于多轮对话：`chat` 复用同一 `session_id` 的历史（JSONL 落盘），MAO 会在会话内起一个带工具的 Agent 处理该会话的消息。无状态派工（`ask`/`ask_many`/`ask_vote`）则每次独立、不接续历史。

#### 会话级工具隔离（可选）

给不同会话不同工具权限，适合多租户/多用途话茬。白名单在 `new_session` 时一次性设定，之后不可改（想换权限就开新会话）。

```json
{"cmd":"new_session","session_id":"sandbox","tools":["run_shell","read_file","list_dir"]}
```

- 白名单之外的本地工具（含 MCP / Skill）在该会话内不可见，越权调用返回错误
- 注意：白名单会连带裁掉协作工具（`ask_worker` / `ask_workers` / `ask_vote` / `run_pipeline`），该会话仍想协作就把它们一并列入白名单
- 不传 `tools` = 放开全部工具，与旧行为一致
- 检查是否生效：`{"cmd":"session_tools","session_id":"sandbox"}`

```json
{"cmd":"session_tools","session_id":"sandbox"}
→ {"ok":true,"session_id":"sandbox",
   "allowed_tools":["run_shell","read_file","list_dir"],
   "removed_tools":["write_file","append_file","ask_worker","ask_workers","ask_vote","run_pipeline"]}
```

> CLI 同能力：`python -m agent run "任务" --stream` 也能以 JSON 事件行输出（与 bridge 事件格式一致），供脚本解析。

## 4. 事件流（stream）

长任务过程默认不可见（只有最终 result）。请求带 `"stream": true` 时，中间过程以事件行即时输出，最后才输出正式响应行。

**事件行例**：

```json
{"event":"llm_call"}
{"event":"tool_start","name":"run_shell"}
{"event":"tool_result","name":"run_shell","preview":"..."}
{"event":"stage","stage":"draft","summary":"起草：3 名工人并行出稿中…"}
{"event":"final","preview":"..."}
```

> 区分：事件行带 `event` 字段、无 `ok`；正式响应行带 `ok` 字段。长文本以 `preview` 截断（工具结果 500 字符、阶段 200 字符）。

**真实调用流程（chat + stream，会话内 Agent 自主派工）**：

```
请求 → {"cmd":"new_session","session_id":"s1"}
请求 → {"cmd":"chat","session_id":"s1","message":"写个 xx 方案","stream":true}
输出 → {"event":"llm_call"}                 （模型思考中）
输出 → {"event":"tool_start","name":"ask_workers"}
输出 → {"event":"tool_result","name":"ask_workers","preview":"### 工人 wsp1 的结果…"}
输出 → {"event":"final","content":"【方案】…"}      （正式结果，可作唯一可信来源）
```

外部主建议：事件行用于展示/日志，最终结果行用于采信。

## 5. 容错行为

| 情况 | 行为 |
|------|------|
| 请求不是合法 JSON | `{"ok":false,"error":"请求必须是 JSON 对象"}` |
| 请求 JSON 解析失败 | `{"ok":false,"error":"JSON 解析失败: ..."}` |
| 未知指令 | `{"ok":false,"error":"未知指令: xxx"}` |
| agent 不存在 | `ask` 返回 `错误：子智能体 'xxx' 不存在...` |
| 无会话调用 chat | `{"ok":false,"error":"会话 'xxx' 不存在，请先 new_session..."}` |
| API key 未配 / 认证失败 | 返回 ok=false + 具体错误；**协议循环不崩溃** |

任何单条指令失败都不会拖垮 bridge，外部主可放心逐条驱动。

## 6. 完整驱动示例（伪代码）

```python
import json, subprocess

proc = subprocess.Popen(
    ["uv", "run", "python", "-m", "agent", "bridge"],
    stdin=subprocess.PIPE, stdout=subprocess.PIPE, text=True,
    encoding="utf-8", bufsize=1,
)

def send(req):
    proc.stdin.write(json.dumps(req, ensure_ascii=False) + "\n")
    proc.stdin.flush()

# 1. 握手
ready = json.loads(proc.stdout.readline())        # {"event":"ready",...}

# 2. 看工具与工人
send({"cmd": "list_tools"})
tools = json.loads(proc.stdout.readline())

# 3. 开个会话持续对话
send({"cmd": "new_session", "session_id": "brf01"})
json.loads(proc.stdout.readline())

# 4. 流式跑任务，边读事件边展示
send({"cmd": "chat", "session_id": "brf01",
      "message": "帮我看看当前目录结构，然后给个整理建议", "stream": True})
while True:
    line = proc.stdout.readline()
    obj = json.loads(line)
    if "ok" in obj:            # 正式响应 = 本轮结束
        final = obj.get("result")
        break
    print("[event]", obj.get("event"), obj.get("name", obj.get("stage", "")))

# 5. 收尾：关会话 / 关闭进程
send({"cmd": "close_session", "session_id": "brf01"})
proc.kill()
```

## 7. 建议的驱动策略

- **小任务**：直接 call_tool，别绕弯派工
- **要多方对比**：`ask_many` 并行派多个工人各出一份，回来看差异
- **要共识/交叉验证**：`ask_vote` 两步投票
- **高质量产出**（方案/报告/代码）：`run_pipeline` 固定三阶段打磨
- **多轮对话 / 想让 MAO 内部 Agent 带着工具自主跑一轮**：`new_session` + `chat`（`stream` 观察）
- **何时不派工**：一次能查证/做完的事自己干；派工要给足背景与验收标准

## 8. 当前限制

- `chat` 必须先 new_session（无"隐式建会话"）
- 同一会话任务串行执行，外部主不要在收到结果前并发发多条 chat
- 会话是进程内状态，bridge 退出即清空（历史仍落盘 data/sessions/，重启可新建会话续上下文编号）
- MCP 连接数量受服务器配置限制，不必事事先连
