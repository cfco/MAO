# 外部主智能体接入指南（bridge 协议）

> 适用对象：任何想把本项目当"手脚 + 工人"用的外部智能体（TRAE / Cursor / Claude Code / 自研脚本等）。
> 核心理念：**谁启动并驱动本项目，谁就是主智能体**；项目只提供本地工具（shell/文件/MCP/Skill）
> 与池内模型工人（纯文本执行器）。MAO 侧**无状态**：没有内部 Agent 循环、没有持久会话，
> 每行请求独立处理、即时应答，历史上下文由外部主自持。

---

## 1. 概念速览

| 角色 | 谁 | 干什么 |
|------|-----|--------|
| 主智能体（大脑） | **你（外部驱动者）** | 拆解任务、调用工具、调度工人、汇总把关 |
| 本地工具（手） | 本项目 | run_shell / 文件读写 / list_dir / MCP 工具 / Skill |
| 工人（子 AI） | 智能体池里的免费模型 | 纯文本执行器：单派、并行对比、投票、评审 |

一句话：**大脑在你那边，项目当外包的手和苦力。**

原先 MAO 自带的"选主自己跑"入口（chat / run / pipeline / web）与持久会话已全部移除，
bridge 是唯一内核。

### 三种接入方式（选一）

同一内核（11 条无状态指令，见 §3）配三种外壳，行为逐字一致：

| 方式 | 命令 | 适合谁 |
|------|------|--------|
| **MCP server（推荐）** | `uv run mao mcp` | 支持 MCP 的宿主（Claude Desktop / Cursor / Qoder 等）：填一段配置即接入，工具自动发现、协议零感知 |
| **one-shot** | `uv run mao call <指令> '<JSON>'` | 只有 shell/技能机制、每次调用起新进程的宿主：一行命令拿一行 JSON，退出码 0/1/2 表成败/指令失败/参数坏 |
| **裸 JSON 行协议** | `uv run mao bridge` | 要长驻、批量、自管子进程进出的深度集成驱动方（本指南 §2.3 以下全部适用） |

MCP 宿主配置示例：

```json
{
  "mcpServers": {
    "mao": { "command": "uv", "args": ["run", "mao", "mcp"], "cwd": "D:/path/to/MAO" }
  }
}
```

one-shot 示例：

```powershell
uv run mao call health
uv run mao call ask '{"agent":"glm-flash","prompt":"这个函数有边界问题吗"}'
uv run mao call call_tool '{"name":"run_shell","args":{"command":"git status --short"}}'
```

> one-shot 每次付进程冷启动成本（配置加载；配了 `mcp_servers` 时还含 MCP 首连）。
> 高频/低延迟场景用长驻的 mcp / bridge 壳。

## 2. 快速开始

### 2.1 配置 API（先用起来）

本项目按「中转站」组织模型：**一个 Endpoint + 一个 Key，可挂多个 Model**（一个站=一个免费 token 多模型）。

配置分两层（互为守卫）：

- `.env.example`（进 git，随仓库维护）：接口地址 + 模型清单 + 空 key 占位。`git pull` 即更新模型，**不要**在这里写真实 key（有测试守着 `*_KEY` 行必须为空）。
- `.env`（不进 git，以点开头，AI 约定不读）：**只写 key**：

```ini
NODE_A_KEY=sk-你的token
NODE_B_KEY=sk-你的token    # 不用 B 站可不写
LLM_API_KEY=sk-同一个key   # 兜底单模型（ask 不指定 agent 时用）
```

> 别把整份 `.env.example` 复制进 `.env`：非 key 变量会盖住 `.env.example` 的模型清单更新，
> 启动时按 `[配置分层提醒]` 点名警告（只报变量名、绝不回显值）。

加载优先级：shell 环境变量 > `.env` > `.env.example`。要改接口/增删模型改 `.env.example`（或设环境变量）即可，不必碰 `.env`。变量名必须与 `config.yaml` 里的 `${...}` 一致，否则填了不生效（`tests/test_config_contract.py` 守住这条契约）。

`config.yaml` 的 `agents` 引用这些变量，示例：

```yaml
agents:
  - name: node-a                      # 中转站 A：一个 token，多模型
    base_url: ${NODE_A_ENDPOINT}
    api_key: ${NODE_A_KEY}
    models: ${NODE_A_MODELS}          # 逗号分隔多个模型，模型可带 @上下文长度
    tags: code,长上下文               # 可选：能力标签，health/list_agents 会回吐
  - name: node-b                      # 中转站 B
    base_url: ${NODE_B_ENDPOINT}
    api_key: ${NODE_B_KEY}
    models: ${NODE_B_MODELS}
```

`.env.example` 里的清单写法示例：

```ini
NODE_A_ENDPOINT=https://你的中转站a/v1
NODE_A_MODELS=gpt-4o-mini@128k,claude-3-haiku@200k
NODE_B_ENDPOINT=https://你的中转站b/v1
NODE_B_MODELS=kimi,glm-4-flash
```

**上下文长度参数**：每个模型可独立标注上下文窗口，格式 `模型名@长度`：
- `@128k` → 128×1024=131072 token；也可写纯数字如 `@200000`（200k）
- **不标 `@` 的模型按默认 128k 处理**
- 作用：`list_agents` 会把 `context_length` 回吐给外部主，供你决定"长上下文活派给谁"。
  MAO 侧已无内部会话，不做历史裁剪——给工人带多少上下文完全由外部主拼 prompt 时自定
- 以上 4 行配置实际展开为 4 个智能体：`node-a:gpt-4o-mini`（131072）、
  `node-a:claude-3-haiku`、`node-b:kimi`、`node-b:glm-4-flash`

**临时屏蔽某个模型**（中转站免费模型经常变，注释即下线，不改代码不重启）：

```ini
NODE_A_MODELS=gpt-4o-mini@128k,claude-3-haiku@200k,#mixtral@32k
```

规则：`models` 里 **`#` 前缀的模型直接跳过**（`#` 后不能有空格，否则会串进模型名）；加回模型删掉 `#` 即可。屏蔽语法可与 `@` 混用（`#mixtral@32k` = 下线一个标过窗口的模型）。

> 历史上还有"连续 N 个运行日失败自动往 `.env.example` 加 `#`"的机制，已移除：
> 按需驱动下，节点去留判断权交给外部主（用 `health` 查当前可用性，人工决定屏蔽）。

**自动展开**：上面会展开成 4 个智能体 `node-a:gpt-4o-mini`、`node-a:claude-3-haiku`、`node-b:kimi`、`node-b:glm-4-flash`。后续 `ask` 的 `agent`、`ask_many`/`ask_vote`/`run_review` 的 `workers` 直接按这些名字引用。旧写法（`model:` 单模型字段）仍然兼容。

改完 `.env` / `.env.example` / `config.yaml` 后**重启 bridge 生效**。

### 2.2 启动 bridge

```powershell
# 在项目根目录（配置好 config.yaml 的 agents / API key 之后）
uv run python -m agent bridge
```

### 2.3 协议格式

- 传输：stdin / stdout，UTF-8
- 格式：**stdin 每行一个 JSON 请求 → stdout 每行一个 JSON 响应**，一一对应
- 启动后第一件事：读一行 `ready` 事件确认握手成功
- **stderr 也保证 UTF-8**：配置警告等诊断走 stderr，bridge 启动即把 stdout/stdin/stderr 归一为 UTF-8（Windows 重定向流默认 GBK，不转码会让按 UTF-8 收 stderr 的驱动方解码报错）。stdout 永远是纯 JSON 行，诊断绝不混入。

**握手示例**（用任意方式读 stdout 首行）：

```
输入：   （无，启动即返回）
输出：   {"ok":true,"event":"ready","version":"0.1.0","agents":["glm-flash","kimi"],"mcp":[]}
```

### 2.4 最小调用

请求行：

```json
{"cmd":"ping"}
```

响应行：

```json
{"ok":true,"version":"0.1.0","agents":["glm-flash","kimi"]}
```

## 3. 指令全表

### 3.1 信息类

| 指令 | 说明 | 示例响应关键字段 |
|------|------|------------------|
| `ping` | 探活 | `ok, version, agents`（名字列表） |
| `list_agents` | 智能体池清单（含能力标签，不含 key） | `ok, agents[{name,base_url,model,context_length,note,tags}]` |
| `health` | **派工前预检**：各子 AI 当前可用性快照 | `ok, workers[{worker,model,tags,available,cooldown_s,quarantined_today}]` |
| `list_tools` | 可用本地工具（内置+MCP+Skill） | `ok, tools[{name,description}]` |

`health` 的 `available=false` 表示当前不可派：冷却中（`cooldown_s` 为剩余秒数）或当日失败隔离
（某模型出现一次**不可重试的终态失败**——如认证失败——后当天不再派工给它；429/5xx/超时等
瞬时失败耗尽重试只进短时冷却，不拉黑全天）。路由取舍由外部主决定。

### 3.2 工具与技能

| 指令 | 说明 |
|------|------|
| `{"cmd":"call_tool","name":"run_shell","args":{"command":"dir"}}` | 执行本地工具（工具名以 list_tools 为准） |
| `{"cmd":"load_skill","name":"技能名"}` | 读取技能全文（frontmatter + 正文） |
| `{"cmd":"run_skill_script","skill":"技能名","script":"脚本.py","args":{}}` | 执行技能内脚本 |

MCP 工具以 `mcp__<服务器>__<工具>` 命名，同样走 call_tool。

文件工具的活动范围 = MAO 项目根 + `config.yaml` 的 `tools.workspace` 所列目录（默认为空，
只认项目根）。要驱动**别的项目**（读写另一个仓库、把 run_shell 的 cwd 指过去），
把那个目录登记进 workspace 即可，详见 README「用 MAO 驱动别的项目」一节。

### 3.3 工人调度（无状态，纯文本执行）

| 指令 | 说明 |
|------|------|
| `{"cmd":"ask","agent":"glm-flash","prompt":"...","system":"可选角色"}` | 单派一个工人 |
| `{"cmd":"ask","prompt":"..."}` | 不指定 agent 时退回兜底单模型（`llm:` 段 + `LLM_API_KEY`） |
| `{"cmd":"ask_many","workers":["w1","w2"],"prompt":"...","system":"可选"}` | 同一任务并行派多个工人；返回 `workers`（逐工人结构化 `worker/ok/status/answer/elapsed_ms`，**顺序与入参一致**）+ `results`（文本版）。缺省 `workers` 用 `pick()`：池内确定性顺序前 `collaboration.max_participants`（默认 5）个当前可派工人 |
| `{"cmd":"ask_vote","prompt":"...","threshold":0.5,"workers":可选}` | 两步投票：先各出方案 → 再对确定性编号投票 → 超阈值宣布共识并附胜出方案全文（废票不进分母） |
| `{"cmd":"run_review","draft":"...","context":"可选背景/验收标准","workers":可选}` | 外部主给初稿，多个工人只当评审团挑错、给编号改进建议；返回结构化 `reviews` |

注意：工人是**纯文本执行器**（不挂本地工具），free 模型 function calling 参差不齐，这样最稳
也最安全；本地工具权始终在主智能体（你）手里。

### 3.4 已移除的指令

`run_pipeline`（固定流水线）、`new_session` / `chat` / `list_sessions` / `session_tools` /
`close_session`（持久会话）、`cancel_tool`、`stream` 参数——均随「单一 bridge 路线」收敛
移除。需要流水线效果时，由外部主自己串：`run_review` 拿评审意见 → 外部主修订 → 再
`ask_vote` 交叉验证。

## 4. 容错行为

| 情况 | 行为 |
|------|------|
| 请求不是合法 JSON | `{"ok":false,"error":"JSON 解析失败: ..."}` |
| JSON 但不是对象 | `{"ok":false,"error":"请求必须是 JSON 对象"}` |
| 未知指令 | `{"ok":false,"error":"未知指令: xxx"}` |
| `ask`/`ask_many`/`ask_vote` 缺 prompt | `{"ok":false,"error":"prompt 不能为空"}` |
| `run_review` 缺 draft | `{"ok":false,"error":"draft 不能为空（外部主给出初稿，子 AI 只当评审团）"}` |
| agent 不存在 | `ask` 返回 `{"ok":false,"answer":"","status":"missing","error":"子智能体 'xxx' 不存在。可用：..."}` |
| 工人在冷却 / 当日隔离 | `ask` 同样 `ok:false`，`status` 为 `cooldown` / `quarantined`；`ask_many` 里对应条目 `ok:false` + 该 status |
| API key 未配 / 认证失败 | 单工人失败如实带回：`ask` → `ok:false, status:"error"`；`ask_many` 里该工人条目 `ok:false`（看 `status` 分型）；**协议循环不崩溃** |
| `call_tool` 工具执行失败 | `{"ok":false,"result":"错误：...","error":"..."}`（`ok` 反映真实成败，不再永远 true） |

`ok` 只认成功：工具与派工失败即 `ok:false`，判断成败看 `ok`/`status`，不必再解析文本前缀。
稳定 status 词表（全内核统一，不做中文翻译）：`ok | error | cooldown | quarantined | missing | timeout`。

任何单条指令失败都不会拖垮 bridge，外部主可放心逐条驱动。免费节点容错（分类重试、
节点冷却、当日隔离、整体限时自适应）见 `REQUIREMENTS.md` §4。

## 5. 完整驱动示例（伪代码）

```python
import json, subprocess

proc = subprocess.Popen(
    ["uv", "run", "python", "-m", "agent", "bridge"],
    stdin=subprocess.PIPE, stdout=subprocess.PIPE, text=True,
    encoding="utf-8", bufsize=1,
)

def send(req):
    proc.stdin.write(json.dumps(req, ensure_ascii=False) + "\n")
    proc.stdin.flush()
    return json.loads(proc.stdout.readline())   # 一问一答，一行一响应

# 1. 握手
ready = json.loads(proc.stdout.readline())      # {"event":"ready",...}

# 2. 派工前预检：看哪些工人现在可用
health = send({"cmd": "health"})
usable = [w["worker"] for w in health["workers"] if w["available"]]

# 3. 本地干活：执行命令
r = send({"cmd": "call_tool", "name": "run_shell",
          "args": {"command": "python -m pytest -q"}})
print(r["result"])

# 4. 关键结论交叉验证：并行派 3 个工人各出一份
r = send({"cmd": "ask_many", "workers": usable[:3],
          "prompt": "这个函数有没有边界问题？给出结论和依据"})
for w in r["workers"]:
    print(w["worker"], w["ok"], w["answer"][:80])

# 5. 收尾：关进程即全部释放（无会话需要关闭）
proc.stdin.close()
proc.wait(timeout=30)
```

## 6. 建议的驱动策略

- **小任务**：直接 call_tool，别绕弯派工
- **要多方对比**：`ask_many` 并行派多个工人各出一份，回来看差异
- **要共识/交叉验证**：`ask_vote` 两步投票
- **高质量产出**（方案/报告/代码）：外部主起草 → `run_review` 评审团挑错 → 外部主修订
- **派工前先看 `health`**：冷却/当日隔离的工人不硬派；按 `tags` 选路
- **何时不派工**：一次能查证/做完的事自己干；派工要给足背景与验收标准

## 7. 当前限制

- 协议循环**串行处理** stdin：一条请求收到响应前发多条，会排队（不是并发通道）
- 每请求超时由 `llm.timeout`（默认 120s）与 `ask_many`/`vote` 的整体限时兜底，外部主读响应时留足耐心
- `ask_many`/`ask_vote`/`run_review` 缺省名单受 `collaboration.max_participants`（默认 5）约束；显式传 `workers` 不受限
- MCP 连接按配置进程内共享（引用计数），不必事事先连
- workspace 目录的读写权随配随给：只登记信任的项目（见 README「工作区」一节）
