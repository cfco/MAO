3单个工人派工 + 容错状态机

这是全项目最关键的"免费节点友好"逻辑。ask_result() 返回结构化 {ok,status,answer,error}、不抛异常——批量路径（collect/vote）按 status 判定，ask() 是其文本包装。

  1. worker 在池里吗？否 → status=missing，返回「错误：子智能体不存在」
  2. 冷却中？_cooldowns 未到期 → status=cooldown，跳过提示（到期自动回来）
  3. 当日失败隔离？ModelHealth 今天记过终态失败 → status=quarantined，"明天再试"
  4. 都通过 → _call_result()：取缓存 LLMClient → chat → 按性质记账
▼ _call_result 结果分路记账（_record_result(name, ok, fatal)）
成功清冷却、连击归零
可重试失败timeout/429/5xx/连接/意外异常 → fatal=False：连击+1、达阈值进短时冷却；不当日隔离，当天仍可回来（#1 修复）
终态不可重试失败auth / 非重试 4xx → fatal=True：冷却 + 记 health.record_failure → 当天隔离

✅ #1/#2 修复后：冷却与当日隔离各司其职——一次瞬时抖动只短时退避，不会"一失败就封一整天"把整池打空。

!读代码时发现的隐患清单

按影响排序。✅ #1–#6 已于 2026-09-22 全部修复（离线全量 126 测试通过 + 变异回归 14 项全绿）；#7–#9 为低优先级，暂未动。各条下方保留原始问题描述，末尾「建议」即落地方案。

✅已修 #1 任何一次失败即"全天隔离"，对免费节点过于激进 orchestrator._call_result → _record_result → health.record_failure

失败路径无条件记当日隔离——包括一次网络 timeout、一次连接抖动、一次 429 限流。免费中转站天天限流/抖动是常态，于是「早上 9 点被限一次 → 该模型今天彻底不派工」。叠加 pick() 只取池内前 5 个存活，很容易把头部 5 个打空后整批隔离，而后面的 35 个模型全程闲置、当天也不轮转。

可考虑：只对"终态不可重试错误"（auth / 4xx）做当日隔离，可重试类（timeout/429/5xx/连接）仅进冷却；或在隔离判定里加"当天失败次数阈值"。

✅已修 #2 冷却层基本被隔离层架空 orchestrator._skip_reason / _record_result

设计是双层：连击达 cooldown_fails(默认2)进冷却（短时、会恢复），终态失败进当日隔离。但两者都由同一次失败触发，而隔离第一次就生效 → 冷却几乎永远轮不到起作用，"指数冷却、成功即恢复"这套逻辑实质被短路。这与 #1 是同一根因的两面。

✅已修 #3 ok 字段不反映真实成败，外部主得靠字符串猜 bridge.handle / ToolRegistry.run / WorkerPool.ask_result

call_tool、ask(带 agent)、ask_many 即使底层失败，也回 {"ok":true, "result/answer":"错误：…"}；而 ask 不带 agent 时 LLMError 会冒泡成 {"ok":false}。同一个"ask 失败"有两种契约形状，且成败信息藏在文本前缀里。外部主要么按 "错误："/"失败：" 前缀解析，要么只能盲信 ok。

可考虑：tool/单 ask 路径也回结构化 status；或统一把底层错误归一到 ok:false + error，answer 只放成功内容。

✅已修 #4 全靠"错误：/失败：/子智能体"魔法前缀做分类 orchestrator.ask_result / collect / vote / _run_ballot

collect/vote 用 out.startswith("错误：") 判失败、用「错误：子智能体 + 标记词」判跳过。这是 stringly-typed 耦合：工人正常回答若以"错误："开头会被当失败丢弃，反过来正常文本里出现冷却字样也可能误判。投票里已经专门为此加注释（怕 429 数字被当成选票）——说明这套脆弱契约已在打补丁。

内部传结构化对象（ok/answer/kind），只在最后渲染成人读文本时再拼前缀。

✅已修 #5 run_shell 黑名单可被解释器轻易绕过 builtin._check_command_safety / _scan_code_body

黑名单锚定"命令首词"，但 python -c "import os,shutil; ..."、powershell -f evil.ps1、node -e 等首词是解释器，正文从不扫描——任意代码照跑，del/format 防护形同虚设。文件工具（read/write/list_dir）有 _resolve 越界防护，但 run_shell 除 cwd + 重定向启发式外不受工作区约束，两套边界不一致：可用 python -c open('/绝对路径','w') 绕过文件沙箱。

若确要"给主一双不受限的手"，就把这点在文档/工具描述里讲明（当前是纵深防御非边界）；否则黑名单应升级为"解释器 -c/-e/脚本文件"的额外拦截，或文件类工具与 shell 共用同一套根约束。

✅已修 #6 pick() 固定取头部 N，默认派工从不轮转、负载不均 orchestrator.pick / _pick_cursor

pick() = live[:cap]，顺序是池内声明序。默认 ask_many/vote/run_review 永远只打同样那 5 个头部节点，其余模型闲置；头部被限流隔离后窗口才缓慢后移。与"多免费 key 分摊额度省 token"的初衷相悖。

默认按 tags / 上次使用时间 / 轮转选 N 个，把额度摊到整池（保持一次调用内顺序确定性即可，无需跨调用固定）。

低 #7 bridge 请求串行，外部主无法并发/中途取消 bridge.serve

for 循环逐行处理，一条长 ask_many（自适应限时可能几分钟）会阻塞整个连接；外部主期间发来的行排队、也无法发"取消"。要并行只能开多个子进程（各自重建 MCP/池）。

低 #8 兜底单模型 ask 不进任何健康体系 bridge._fallback_client

不带 agent 的 ask 直连 LLMClient，不记冷却/隔离、不复用工人缓存，与主路线容错语义割裂；且 Config.raw = data 存的是插值后数据（命名易误解为原始）。属边角一致性。

低 #9 文档 / 注释漂移 config.yaml 头注释 · orchestrator 头注释

  • config.yaml 仍写"被选中/指定的那个当主智能体""solo/兜底路径"，但这些入口已随"仅 bridge"移除。
  • orchestrator 头注释提"swarm 模式/ask_worker 工具/M5 LRU 缓存"，正文已删；health.record_failure 的 model/models_env 参数、active_dates 均已成死字段。
  • _split_models 把 @128k 按 1024 折 token，与"k≈1000"惯例有偏差（影响极小）。
