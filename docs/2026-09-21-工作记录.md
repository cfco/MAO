## 项目：MAO 自研多智能体协作系统

### 一、立项讨论与方向决策

**起点问题**：不使用别人做好的智能体当主 AI，会不会不方便接入 MCP 和 Skill？

**结论**：方向反了——自建主控不会变难，真正受限的是拿成品智能体当主控（黑盒、不可控）。
- MCP 是开放协议（官方 Python/TS SDK），自研接入几十行代码的事
- Skill 本质是"能力包"组织方式，自建可以完全自定义机制
- 讨论中区分了三个层次：成品智能体（不适合当主）、成熟框架（快速起步）、纯自研（最可控）

**主人拍板的三项决策**：
1. 底座路线：自研主控
2. 形态：网页/App 对话助手 + 本地自动化工具（双形态）
3. 技术栈：Python

### 三、v2：方向升级为多智能体协作（核心变更）

**主人明确项目最终目标**：不是单模型智能体，而是"**三个臭皮匠顶个诸葛亮**"——多个免费、较慢、较弱模型分工协作产出高质量结果。

**主人定下的主智能体机制**（完全按此实现）：
- 用某个智能体启动/驱动本项目 → 它就是主智能体
- 其它 API 接入的全部作为子智能体（工人）
- 只有 CLI 窗口或 Web 等非智能体入口启动时，才从 API 池中选一个当主

**v2 落地内容**：
1. **智能体池**：config.py 重构，`AgentProfile`（name/base_url/api_key/model/note），config.yaml 的 `agents` 列表，免费档模型随便进池
2. **工人池 WorkerPool**（agent/core/orchestrator.py）：
   - `ask_worker`：单派子任务（工具化）
   - `ask_workers`：同一子任务并行派多人，多方案对比/交叉验证/取共识（线程池并行，单工人失败不拖垮整体）
   - 设计要点：派工做成**主智能体的工具**，主自主决定拆解/派工/汇总时机，哪怕主也是弱模型
   - 工人=纯文本执行器（不挂本地工具）：免费模型 function calling 参差不齐，纯文本最稳；本地工具权集中在主手里，安全
3. **bridge 协议**（agent/bridge.py）：`python -m agent bridge`，stdin/stdout JSON 行协议（UTF-8），指令集 ping / list_agents / list_tools / call_tool / load_skill / run_skill_script / ask / run_task——任何外部智能体驱动即为主
4. **CLI 四子命令**：bridge / chat（交互选主）/ run / web
5. **Web 选主**：/api/agents 端点 + 顶栏下拉切换主智能体（切换即新会话）
6. swarm（自主协作）与 solo（单干）两种模式，`--solo` 开关
7. 文档同步：架构方案.md 升级 v2、README 重写
